## ABI evidence and unresolved closure

[Windows static inventory](../../resources/manifests/native-windows-x64.json) records **456** PE files: Electron 7, standalone Node 1, PostgreSQL 159, existing Torch/Python component 288 and build-only Next SWC 1. It parses both normal and delay import descriptors and machine fields. Six setuptools template executables are x86/ARM64; they are inventory findings requiring an explicit packaging decision, not evidence of executing a mixed-ABI stack. The scanner includes optional PG modules and wheel install/build helpers, so not every scanned file is a required runtime consumer.

PostgreSQL imports external `msvcp140.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`. Python's package has a copy of `msvcp140.dll` nested in sklearn's `.libs`; its basename does not make it visible to Torch's loader. Earlier actual inference loaded the host System32 copy, so a static cross-directory basename match cannot close the gap. Torch also imports `vcomp140.dll`; its wheel supplies a candidate file but clean loader origin, license and CPU feature evidence remain required. The CRT inventory alone does not prove correct app-local provisioning.

The Node Windows child actually reports module ABI 127 / Node-API 10. The earlier Electron utility child reported ABI 150 / Node-API 10. Use standalone Node children for Next/Express and do not load their native modules into Electron. SWC load is a build-component probe, not the complete production closure. Browser/media/native libraries loaded by name at runtime, exported symbol/version constraints, plugin discovery and CPU instructions are outside a static import scan.

For Linux, capture `readelf -h -d --version-info`, actual glibc/GLIBCXX/CXXABI requirements and `ldd`/loader maps for every native object on Ubuntu 22.04 and Debian 12. Identify bundled versus explicitly allowed OS libraries; ship permitted non-OS dependencies with correct RUNPATH and relocation. The official Node v22.22.0 [build platform table](https://github.com/nodejs/node/blob/v22.22.0/BUILDING.md) is an upstream baseline, not a Dozu run. CPU-only Torch must use the pinned CPU-index candidate, not assume the default PyPI Linux wheel excludes CUDA.

For macOS, capture `file`, `lipo -info`, `otool -L/-l`, deployment minimums, install names/@rpath and code-signature verification on **both** Intel and ARM64. Select macOS-13-compatible NumPy/SciPy wheels instead of silently selecting macOS-14 variants. Torch 2.9.1 has no Intel wheel in the recorded metadata; upstream [2.2 announcement](https://pytorch.org/blog/pytorch2-2/) names 2.2.x as the last macOS x64 line. An older Torch/Python package closure or a different backend needs an explicit compatible/security-reviewed solution; do not make ONNX mandatory or change the model to hide the gap.

All native gates require a clean machine without developer libraries, startup/model/actual consumer workflows and captured loaded-library origin. This host is Windows 11 Pro 10.0.26300 x64, i5-13400F, about 34 GB physical RAM; it is not clean or the accepted 8 GB/four-core minimum. No Windows 10, macOS or Linux target was run here.
